# Source guide

Use this catalog to resolve specific editorial questions. Follow project-specific conventions first. Prefer primary standards and platform terminology over secondary summaries.

## Primary style and structure sources

- [Google developer documentation style guide](https://developers.google.com/style): use for developer-documentation language, grammar, organization, linking, formatting, accessibility, and global-audience guidance.
- [Google style highlights](https://developers.google.com/style/highlights): use as a concise editorial checklist.
- [Google voice and tone](https://developers.google.com/style/tone): use for a conversational, friendly, respectful voice without slang or frivolity.
- [Google text-formatting summary](https://developers.google.com/style/text-formatting): use for bold, italics, code font, capitalization, quotation marks, and punctuation.
- [Google cross-references and linking](https://developers.google.com/style/cross-references#descriptive-link-text): use for descriptive, accessible link text.
- [Google accessible documentation](https://developers.google.com/style/accessibility): use for headings, links, images, tables, and nonvisual cues.
- [Google global-audience guidance](https://developers.google.com/style/translation): use for translatable language and culturally neutral examples.
- [Google future-features guidance](https://developers.google.com/style/future): use to keep unapproved future behavior out of released documentation.
- [Microsoft Writing Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/): use as a searchable fallback for technology terminology and crisp, bias-free communication.
- [Apple Style Guide](https://support.apple.com/guide/applestyleguide/about-the-guide-apsg1eef9171/1.0/web/1.0): use for Apple product terminology, user-interface text, inclusive writing, technical notation, and international style.
- [Diataxis](https://diataxis.fr/): use to separate tutorials, how-to guides, reference, and explanation according to reader need.
- [Write the Docs guide](https://www.writethedocs.org/guide/): use for documentation practice, accessibility, docs-as-code, tooling, and maintenance context.

## Requirements and controlled language

- [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174): use for normative obligation keywords. Only uppercase forms carry the defined BCP 14 meanings.
- [ASD-STE100](https://www.asd-ste100.org/): use the principles of controlled technical language to reduce ambiguity for global readers. Do not claim full ASD-STE100 compliance without applying the licensed standard and its dictionary.
- [ISO 24495-1:2023](https://www.iso.org/standard/78907.html): use as the formal plain-language foundation. Do not claim ISO compliance from this skill alone; the full standard is not bundled.

## Supplemental background

- [QuillBot technical-writing overview](https://quillbot.com/blog/content-writing/what-is-technical-writing/): use for broad artifact examples and audience calibration, not as a normative authority.
- [HubSpot technical-documentation overview](https://blog.hubspot.com/service/technical-documentation): use for general documentation workflow and self-service context, not as a normative authority.
- [The First Technical Writer in English: Geoffrey Chaucer](https://www.jstor.org/stable/43094120): treat as historical background, not operational style guidance.

## Context-engineering guidance

- [Anthropic's context-engineering article](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models): use for agent-facing instructions. Keep core guidance lightweight, use progressive disclosure, place exact constraints near the relevant action, prefer rich source artifacts, and avoid restating information an agent can inspect directly.

Do not copy a source's wording at length. Distill the applicable rule, cite the source when the output needs attribution, and verify time-sensitive platform terminology before publication.
